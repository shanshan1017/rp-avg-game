# 视觉小说制作教程总结

本文总结本地图片教程：

```text
<WORKSPACE_ROOT>/tutorial/视觉小说/
```

这不是逐字 OCR，而是把图片教程里的制作逻辑提炼成我们可复用的 AVG / 互动视频游戏工具链指导。

## 1. 核心定义

视觉小说不是“小说 + 插图”。

更适合我们工具链的公式是：

```text
视觉小说 = （叙事 + 视觉 / 听觉演出）x 交互性
```

所以每个可玩单元都必须回答三个问题：

- 叙事：玩家在这一段理解了什么、感受了什么、怀疑了什么、决定了什么？
- 演出：背景、立绘、CG、视频、UI 提示、声音、节奏，如何帮助玩家更容易感受到这些信息？
- 交互：玩家能做什么选择？游戏如何明确反馈“我的选择改变了体验”？

如果一个单元只有文字，也要通过分段节奏、UI 状态和选择反馈来形成可玩性。如果一个单元只有图或视频，也必须有足够的叙事框架，让玩家知道自己是谁、在哪里、发生了什么、为什么重要。

## 2. 完整开发流程

教程把视觉小说制作拆成五个阶段：

1. 构思与策划
2. 剧本与分支设计
3. 美术与听觉资源准备
4. 引擎 / 运行时选择
5. 组装、测试、打磨与发布

映射到我们的工具链，应当是：

```text
项目输入
-> 一致性总规划
-> 故事图规划
-> 世界观 / 角色 / 机制基线
-> 场景戏剧计划
-> 分段剧本
-> 美术 / UI / 音频 / 视频 prompt 计划
-> Runtime Game Package
-> 文本试玩
-> 素材生成
-> 运行时组装
-> Cross-Disciplinary Coherence QA
```

关键点：剧本、美术、音频、UI、运行时不能各做各的。它们必须围绕同一个玩家体验共同设计。

## 3. 构思与策划

开始写细节前，先确定玩家的核心体验。

策划阶段要问：

- 玩家体验的是恋爱、悬疑、恐怖、日常、喜剧、悲剧，还是策略？
- 开始两分钟内，玩家应该感受到什么？
- 推动故事前进的核心压力是什么？
- 主要冲突是什么，而不只是“设定是什么”？
- 哪些世界规则会真正影响剧情？
- 哪些角色是核心角色？每个人想要什么？
- 玩家可以真正影响什么？

这应固化成项目 intake 字段：

- 类型与情绪目标；
- 目标游玩时长；
- 视角；
- 玩家身份；
- 时代与地点；
- 主要角色；
- 中心冲突；
- 分支和结局数量；
- 交互密度；
- 媒体预算；
- 允许的素材类型；
- 是否允许付费生成。

## 4. 剧本与分支设计

教程强调：先做剧情结构，再写正文。

剧情结构至少有三层：

- 主线：所有玩家都必须理解的部分。
- 分支点：玩家做选择的位置。
- 个人线 / 角色线：路线专属剧情和情绪回报。

对我们来说，`story_graph_plan.json` 必须在最终 prose 之前完成。

一个好的故事图规划应该包含：

- 开场交代：玩家是谁、在哪里、现在要做什么；
- 主线知识：所有路线都必须传达的信息；
- 路线知识：某条线才会知道的秘密、情感和证据；
- 分支目的：每个选择测试真实的价值、欲望、风险或关系；
- 选择回声：选择后必须有可见反馈，不能立刻无解释跳远；
- 失败逻辑：中途失败要有原因、后果和收束；
- 结局逻辑：结局要回收之前的选择和证据。

教程里还有一个实用写法：卡住时不要强迫自己从头顺序写，可以先写高潮、关键情绪场、反转场，再回头补连接。我们的工具可以允许 writer 先写锚点场景，但最终必须经过连续性检查。

## 5. 场景写作标准

我们现在的问题之一，是很多场景只是在快速总结剧情，没有真正“演出来”。

每个场景都要有：

- 场景目的：这场为什么存在；
- 玩家上下文：玩家进入场景前知道什么；
- 当前情境：画面里现在正在发生什么；
- 角色欲望：在场角色此刻想要什么；
- 阻力：是什么让角色不能直接得到想要的东西；
- 场景转折：场景结束时发生了什么变化；
- 视觉证据：玩家能看到、听到、检查到什么；
- 文本证据：对白、旁白、系统 UI 如何帮助理解；
- 下一步压力：玩家为什么要继续往下走。

运行时文字不能是一大段说明。应使用短 `segments`，让玩家一段一段点击推进：

```json
{
  "speaker": "player",
  "segments": [
    "最后一节课结束后，教室里只剩下我和黑板旁的校园祭流程表。",
    "我负责在第一束烟火前确认三件事。",
    "手机震动时，星形护符也在书包侧袋里发烫。"
  ]
}
```

这种节奏可以让玩家先消化处境，再进入选择。

## 6. 美术资源分类

教程把视觉资源拆成几个实用类别：

- 角色立绘：核心角色需要基础姿态和多种表情。
- 背景：教室、走廊、卧室、街道、舞台、天台等常用场景。
- CG / 关键插图：重要情绪点、路线高潮、收集奖励。
- UI：对话框、菜单、按钮、选择面板、存读档、路线记录、系统提示。
- 听觉资源：BGM、环境音、音效，必要时可加语音或关键台词。

对我们的工具来说，每个素材都必须回答：

- 它在哪里用；
- 哪个场景或节点需要它；
- 它表现哪个角色、地点或道具；
- 它是必需还是可选；
- 它是否需要参考图保持风格一致；
- 它是立绘、背景、CG、视频首帧、UI 皮肤，还是音频。

不要因为“可能好看”就生成素材。只生成能映射到 runtime 使用位置的素材。

## 7. 角色立绘要求

AVG 的角色展示不是装饰，而是剧本的一部分。

每个重要角色都应该有：

- 设计简介：年龄段、身份、轮廓、服装逻辑、关键视觉符号；
- 性格与说话方式；
- 与玩家的关系；
- 路线或剧情功能；
- 基础立绘；
- 表情集合；
- 可选姿态变体；
- 一致性 prompt；
- 禁止漂移说明。

最小可用表情集合：

```text
neutral, soft, embarrassed, serious, angry, worried, hurt, resolved
```

writer 应该按语义请求表情，例如“担心”“强撑冷静”“松了一口气”，而不是直接写死文件名。美术和 runtime 再把语义状态映射到具体 asset id。

## 8. 引擎与运行时启示

教程建议初学者使用视觉小说引擎，因为它原生支持：

- 角色；
- 对白；
- 标签 / 节点；
- 选择；
- 变量；
- 存档；
- 音乐；
- 转场。

对我们来说，对应的是一个固定 HTML runtime，由可热插拔 JSON 驱动。

runtime 应支持：

- 加载 / 卸载游戏包；
- 开始游戏 / 继续游戏；
- 存档槽；
- 章节选择；
- 结局记录；
- 成就；
- 设置；
- 分段对白；
- 背景切换；
- 角色立绘层；
- 表情切换；
- CG 和视频片段；
- 音频 cue；
- 选择；
- 变量 / flag；
- 路线门槛；
- 失败和结局页。

关键规则：除非明确批准为原型例外，否则不写故事专属 runtime 代码。

## 9. 组装与演出

教程把组装看成一次小型演出调度：

- 把剧本、立绘、背景、BGM、UI 放进引擎；
- 决定立绘何时出现、离场、切表情；
- 决定音乐何时淡入淡出；
- 决定背景何时切换；
- 决定 CG 何时打断普通对话；
- 调整转场、画面效果、节奏；
- 把逻辑和演出放在一起测试。

在我们的工具里，这些不应该只写在 prose 里，而要进入 `runtime_game_package.json`。

一个可玩节点应包含：

- background id；
- visible characters；
- expression changes；
- dialogue / narration segments；
- UI hints；
- choices；
- state changes；
- next node；
- optional media cue。

## 10. 测试标准

教程提醒：就算是文字游戏，也会有 bug，比如死循环、条件断裂、逻辑断层、结局不可达。

我们的 QA gate 应检查：

- 每个 choice target 存在；
- 每条路线能到达结局；
- 每个结局可达；
- 每个失败有清晰触发原因；
- 每个关键角色首次出场时有足够上下文；
- 每个视觉事实有素材或 runtime 替代方案；
- 每个素材至少被一个节点使用；
- 每个选择都有可见回声；
- 每条路线保持玩家知识边界；
- segment 长度适合点击阅读；
- 开始几分钟内交代玩家身份、地点、压力和利害关系。

## 11. 发布与规模控制

教程提到了常见发布平台，但更重要的启示是：视觉小说看似轻量，其实会同时消耗很多工种。

即使是小作品，也会涉及：

- 故事；
- 角色设计；
- UI；
- 背景；
- CG；
- 音频；
- 脚本；
- 测试；
- 打包发布。

所以 Planner 必须在执行前做规模预算：

- 目标游玩时长；
- 节点数量；
- 每节点平均 segment 数；
- 分支数量；
- 结局数量；
- 立绘数量；
- 背景数量；
- CG 数量；
- 视频数量；
- 生成成本；
- QA 成本。

## 12. 对我们工具链的直接影响

这份教程强化了五条规则：

1. 第一个可玩段落必须先让玩家理解处境，再进入重大选择。
2. 先有剧情结构，再有正文；但最终正文前必须有场景戏剧计划。
3. 美术不是装饰，而是证据、情绪、节奏和奖励。
4. 选择需要可见反馈，不能只有隐藏数值变化。
5. 最终交付物应是固定 runtime 可读取的游戏包。

## 13. Agent 分工启示

Planner 负责：

- 目标体验；
- 游玩时长；
- 规模预算；
- 故事图；
- 路线矩阵；
- 必要媒体表面；
- 验收 gate。

Story Graph Director 负责：

- 主线节点；
- 分支节点；
- 路线节点；
- 失败节点；
- 结局；
- 玩家知识边界；
- 选择后果。

Scene Dramaturgy Agent 负责：

- 场景目的；
- 角色欲望；
- 冲突；
- 场景转折；
- 首次出场交代；
- 证据需求；
- segment 预算。

Narrative Writer 负责：

- 分段文本；
- 对话节奏；
- 角色声线；
- 可见选择回声；
- 路线内自洽理解。

Art / UI / Audio Agent 负责：

- 风格圣经；
- 角色设计 prompt；
- 表情列表；
- 背景列表；
- CG 列表；
- UI 皮肤 prompt；
- 音频 cue 计划；
- 素材到场景的映射。

Runtime Agent 负责：

- 合法 runtime package；
- 数据驱动场景；
- 不做故事专属硬编码；
- 支持立绘、背景、CG、视频、选择、存档、结局、成就。

Checker Agent 负责：

- 跨学科一致性；
- 路线可达性；
- 素材与剧情 traceability；
- 节奏；
- 开场理解；
- 选择反馈；
- runtime package 可加载性。

## 14. 后续项目检查清单

启动执行 agents 前，必须确认：

- 玩家能在第一次重大选择前回答“我是谁、我在哪、发生了什么、为什么现在重要”。
- 每个核心角色都有身份、欲望、说话方式、路线功能和视觉钩子。
- 每个分支都测试了有意义的东西。
- 每个选择都有即时可见反馈。
- 每个 CG / 视频都用于情绪、戏剧或信息高峰。
- 每个素材都会出现在 runtime package 里。
- 每个 runtime package 字段都能被程序检查，而不是只能靠人工读 prose。
- 付费生成前可以先完成文字试玩。
